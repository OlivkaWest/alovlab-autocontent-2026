# ALOVLAB ACADEMY STANDARD — полноценные практические учебники (с 16.10.2026, высший приоритет)

> Применять при любом Reels, к которому предусмотрена методичка. Заменяет прежний формат
> «поверхностная PDF-методичка на 5-10 страниц» для таких случаев. GLOBAL-METHODOLOGY-RULE.md
> остаётся базой (структура, честность, «путь в команду») — этот файл добавляет требования к
> глубине и формату, когда методичка работает как полноценный учебный модуль, а не конспект.

## 0. Принцип

Reels привлекает внимание и показывает результат. Карусель раскрывает отдельные приёмы. Методичка
объясняет, как человек повторяет результат своими руками — самостоятельно, без посторонней помощи.
Курс — следующая ступень. Материалы логически связаны, но методичка работает и сама по себе.
**Главный критерий готовности:** человек прочитал методичку → сделал результат своими руками, без
посторонней помощи. Не смог — материал не готов, переделать.

## 1. Роль при написании

Методолог + автор практических учебников по ИИ + технический специалист по конкретным инструментам
темы + технический редактор + UX-инструктор для новичков + арт-директор AlovLab. Сложность содержания
не должна становиться сложностью языка — человек без технического образования понимает каждый шаг.

## 2. Источники — обязательное исследование перед написанием

Перед текстом — проверить официальную документацию инструментов темы (не только блоги). Указывать
источник у каждой важной технической инструкции. Если источники расходятся — не выбирать молча:
явно показать расхождение и сказать, что проверить самостоятельно (пример: разброс в требуемой длине
образца голоса для Instant vs Professional Voice Cloning между источниками — честно обе цифры с
пометкой, какая откуда). Не считать старые названия кнопок актуальными автоматически. Не придумывать
функции, которых не нашли в источниках. Если прямой доступ к документации заблокирован сетью среды —
использовать WebSearch (не WebFetch) и честно пометить, что это вторичное подтверждение, не прямой
просмотр страницы.

## 3. Схема объяснения любого действия в интерфейсе

ГДЕ НАХОДИМСЯ → ЧТО НАЖИМАЕМ (точное название раздела/кнопки по источникам) → ЧТО ПОЯВЛЯЕТСЯ →
ЧТО ВВОДИМ (конкретный пример, не абстракция) → ЗАЧЕМ ЭТО ДЕЛАЕМ → ЧТО ДОЛЖНО ПОЛУЧИТЬСЯ →
КАК ПРОВЕРИТЬ → ЕСЛИ НЕ ПОЛУЧИЛОСЬ (причина + исправление).

Запрещены инструкции без этой раскладки: «настройте голос», «подключите API», «создайте аватар»,
«оптимизируйте параметры» — без пошагового объяснения.

## 4. Две траектории в одном техническом уроке

**Уровень 1 — новичок.** Первый результат через интерфейс, без программирования. Человек не знает,
что такое API, voice ID, модель синтеза — объяснять с нуля.
**Уровень 2 — продвинутая практика.** API, безопасное хранение ключей, Python-интеграция, запросы,
обработка ошибок, автоматизация. Не смешивать уровни в одной инструкции — сначала инструмент через
интерфейс, потом автоматизация.

## 5. Реальные скриншоты, не выдумка

Если нет доступа к реальному интерфейсу (нет своего аккаунта с нужными настройками, сеть заблокирована,
и т.п.) — **не создавать выдуманный скриншот и не выдавать его за настоящий.** Вместо этого: честная
текстовая/табличная схема действия, со ссылкой на источник, и прямая пометка, что скриншот не создан —
какой этап требует реального доступа пользователя, который нужно предоставить отдельно (реальный вход
в аккаунт, подтверждение прав и т.п.).

## 6. API/код — без псевдокода

Рабочие примеры (Python/curl) только по проверенным текущим SDK-вызовам из официальной документации,
не из устаревших туториалов. Каждая строка объясняется простыми словами. Если пример не протестирован
на реальном аккаунте — честно сказать: «проверено по документации, не протестировано на живом
аккаунте» (не изображать проверку, которой не было). Никогда не просить вставлять реальный API-ключ
в публичный документ/код — только через переменные окружения (`.env`, `.env.example`), с объяснением
почему.

## 7. Практическое правило примеров

Каждый практический раздел: пример входных данных → точное действие → пример результата → как
проверить. Не писать «система создаст качественный голос» — показать какой текст ввели, что получили,
как оценили. Промпт — полный, не «попросите нейросеть...». Код — полный рабочий, не заглушка.

## 8. Объём и архитектура

Ориентир 35-60 содержательных страниц, если тема того требует — не растягивать искусственно и не
резать, если нужно больше. Опорная архитектура (адаптировать под тему, не копировать механически):
что мы создаём (со схемой пайплайна) → что нужно подготовить (честно: бесплатно/платно, лимиты,
тарифы проверены на дату) → базовый навык с нуля, самая подробная часть (ключевая глава) → настройка
качества → работа с текстом/сценарием → готовые промпты (минимум 5, полная структура: роль, контекст,
входные данные, задача, ограничения, формат, критерии + пример полного ответа) → API для новичков
(простые аналогии → создание ключа → первая генерация → curl → практика → автоматизация → таблица
ошибок) → второй инструмент с нуля (та же глубина) → интеграция первого и второго инструмента (точная
последовательность, оба маршрута если есть варианты) → тестирование результата (проверочная карта) →
типичные проблемы (симптом → причина → как проверить → исправление) → безопасность и права (согласие,
хранение ключей, запрет на обман/мошенничество) → финальный практический проект (пронумерованная
последовательность, человек реально получает результат) → бонусные материалы (чек-листы, шаблоны,
готовые скрипты).

## 9. Стиль текста

Наставник рядом, который показывает на экране — не академическая лекция, не документация для
программистов. Разговорные обороты уместны («закинь запись», «вот тут многие ошибаются»), без
перегруза сленгом. Термин — сначала простыми словами. Запрещённые обороты — те же, что в CLAUDE.md
§8 («в современном мире», «важно понимать», «революционная технология», «раскрой потенциал»,
«данный инструмент позволяет», «давайте рассмотрим», «инновационное решение»).

## 10. Визуал

Премиальный светлый стиль AlovLab (та же система, что в действующих методичках: светлая основа,
тёмные плашки под промпты, поля/типографика по GLOBAL-METHODOLOGY-RULE и Приложению В CLAUDE.md).
Логотип — только `assets/img/logo-mark.png`. Реальные скриншоты, нумерованные шаги, сравнительные
таблицы, блоки «плохо/хорошо» — где доступны проверенные источники; честная схема вместо
несуществующего скриншота, где источника нет.

## 11. Формат финального продукта (по запросу на материал, не всегда всё сразу)

PDF (оглавление, схемы, примеры, упражнения) — обязателен всегда. По запросу дополнительно: DOCX
(редактируемая версия), отдельный сборник промптов в Markdown, папка с кодом (requirements.txt,
`.env.example`, README по запуску), отдельные файлы чек-листов, короткая Telegram-версия с переходом
к полному материалу, «паспорт актуальности» (дата проверки источников, список ссылок, что
подтверждено/что нет), список контрольных заданий ученика.

## 12. Процесс для каждого обучающего Reels с методичкой

REELS → анализ темы → исследование инструментов (источники по §2) → проектирование урока (две
траектории) → пошаговый туториал (схема §3) → практика → промпты → примеры результатов → типичные
ошибки → чек-листы → готовая методичка. Вторую версию самого Reels вместо методички не делать —
монтажный процесс Reels отдельно, методичка дополняет, не заменяет и не ломает его.

## 13. Аудит перед сдачей

Не присваивать 10/10 автоматически. Если ученик не выполнит шаг без посторонней помощи — переделать
фрагмент. Код без нужной настройки — исправить. Шаг ссылается на несуществующую кнопку — исправить.
Утверждение не подтверждено источником — проверить или убрать.

## 14. Партиями (связь с CLAUDE.md §10)

Учебник такого объёма не пишется одним проходом. Исследование и архитектура — отдельный шаг, затем
главы батчами (по 1-3 главы на проход), с промежуточным сохранением в файл и чекпоинтом у
пользователя перед следующим батчем — тот же принцип, что для контент-плана на месяц.
